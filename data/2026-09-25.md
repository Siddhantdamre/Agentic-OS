Today's focus was investigating, addressing, and verifying fixes for authentication, login flow resilience, redirect security, and OAuth provider discovery.

### 1. Hybrid Auth Fallback & Logout Handling

**Problem:**
- When SuperTokens was booted and initialized, calling `EmailPassword.signIn('public', email, password)` would return `status: 'WRONG_CREDENTIALS_ERROR'` for any user who originally registered directly in PostgreSQL (e.g. during a SuperTokens service outage, local database seed, or container restart).
- The route previously short-circuited on `WRONG_CREDENTIALS_ERROR` and returned `401 Incorrect email or password.`, completely locking out valid PostgreSQL users without checking the database `password_hash`.
- `POST /api/auth/logout` and `POST /api/auth/signout` were not handled in the `POST` handler, causing standard form and API post logouts to fail with `400 Email and password are required`.

**Changes Made:**
- In `apps/dashboard/app/api/auth/[[...path]]/route.ts`:
  - Added support for `logout` and `signout` in the `POST` handler, clearing session cookies and returning `{ status: 'OK' }`.
  - When SuperTokens returns `WRONG_CREDENTIALS_ERROR`, the code no longer rejects immediately; instead, it falls through to verify the credentials against PostgreSQL using `verifyPassword(password, user.password_hash)`.
  - If authenticated via PostgreSQL fallback, the handler opportunistically calls `EmailPassword.signUp('public', email, password)` to sync the user into SuperTokens and links the `supertokens_id` for subsequent sign-ins.

### 2. Redirect Loop and Open Redirect Hardening

**Problem:**
- In `apps/dashboard/app/(auth)/login/page.tsx` and `register/page.tsx`, the `redirect` search parameter only checked `redirectTo.startsWith('/')`.
- This allowed protocol-relative URLs (e.g. `//attacker.com`), which browsers treat as cross-domain redirects.
- In addition, if a user visited `/login?redirect=/login` or `/api/auth/logout`, signing in would redirect right back into a loop or immediately log them out.

**Changes Made:**
- In `apps/dashboard/app/(auth)/login/page.tsx` and `apps/dashboard/app/(auth)/register/page.tsx`:
  - Added strict redirect sanitization:
    ```typescript
    const rawRedirect = searchParams?.get('redirect');
    const safeRedirect =
      rawRedirect &&
      rawRedirect.startsWith('/') &&
      !rawRedirect.startsWith('//') &&
      !rawRedirect.startsWith('/login') &&
      !rawRedirect.startsWith('/register') &&
      !rawRedirect.startsWith('/api/')
        ? rawRedirect
        : '/';
    ```
  - Redirects securely to `safeRedirect` (or `/onboarding/name` if organization onboarding is incomplete).

### 3. Dynamic OAuth Provider Discovery & Inline Feedback

**Problem:**
- Social OAuth buttons (Google, GitHub, Meta, Microsoft) were hardcoded in `login/page.tsx`.
- Clicking an unconfigured OAuth provider bounced the user to `/api/auth/oauth/[provider]` and back to `/login?error=...`, creating a poor user experience.

**Changes Made:**
- In `apps/dashboard/lib/oauth-providers.ts`:
  - Added `listOAuthProviders()` returning each provider's configuration status based on client ID / secret env variables and `demoAuthAllowed()`.
- Created `apps/dashboard/app/api/auth/oauth/route.ts`:
  - Endpoint `GET /api/auth/oauth` returning available providers and `configured: boolean`.
- In `apps/dashboard/lib/session-cookie.ts`:
  - Whitelisted `/api/auth/oauth` as a public API path in `isPublicApiPath`.
- In `apps/dashboard/app/(auth)/login/page.tsx`:
  - Dynamically fetched `/api/auth/oauth` configuration alongside `/api/auth/sso`.
  - If a user clicks an unconfigured provider, the client immediately displays an inline message (`"${providerName} sign-in is not configured on this workspace."`) without initiating a dead-end server redirect.

### 7. Complete TrueForge Runtime Graduation & Integration

**Problem:**
- `inprocessTurnsEnabled()` in `services/workflows/src/local-turn.ts` previously checked `process.env.DAREX_INPROCESS_TURNS === 'true'`, remaining an opt-in toggle rather than the default execution engine.
- `localModelConfig()` prioritized `LITELLM_BASE_URL` over `OPENROUTER_API_KEY` even when `TRUEFORGE_MODEL` was explicitly configured with an OpenRouter model (e.g. `openrouter/deepseek-v4-1-flash`). In environments where LiteLLM was offline or omitted, turns failed with connection errors instead of routing directly to OpenRouter.
- In Ask AI (`apps/dashboard/app/api/ask-ai/route.ts`), sessions were keyed by `dailySessionKey(args.userId)` (`askai-${userId}-${day}`), which forcibly severed conversation context every day at midnight UTC.
- Fallback strings in `services/workflows/src/growth/preferences.ts` and `services/workflows/src/customer/obligation-extractor.ts` still referenced legacy `'atomic-agent'`.

**Changes Made:**
1. **Default In-Process TrueForge (`@truefoundry/trueforge-core`) Execution**:
   - In `services/workflows/src/local-turn.ts`:
     - Updated `inprocessTurnsEnabled()` to default to `true` (`process.env.DAREX_INPROCESS_TURNS !== 'false'`), making in-process TrueForge the canonical, zero-overhead execution harness across DareX.
     - Upgraded `localModelConfig()` to intelligently detect `OPENROUTER_API_KEY` and route directly to OpenRouter when `TRUEFORGE_MODEL` specifies an OpenRouter model (`openrouter/deepseek-v4-1-flash`, `openrouter/gemini-2-5-flash`, etc.) or when LiteLLM is unconfigured.
2. **Conversation-Scoped Session Persistence**:
   - In `apps/dashboard/app/api/ask-ai/route.ts`:
     - Replaced `dailySessionKey` with `resolveSessionKey(args.userId, args.conversationId)` (`askai-${userId}-${conversationId}`), preserving conversational memory and short-term agent recall permanently within each conversation thread without arbitrary daily resets.
3. **Legacy Clean-up**:
   - Replaced `'atomic-agent'` fallback models in `growth/preferences.ts` and `customer/obligation-extractor.ts` with `darex-default`.
4. **Verification & Testing**:
   - Executed `infra/scripts/test-subagents-and-openui.js`:
     - **Test 1 (Generative OpenUI)**: Verified interactive OpenUI component emission (`Stack`, `Table`, `Callout`) via `openUI` capability with `deepseek/deepseek-v4.1-flash`.
     - **Test 2 (Dynamic Subagents)**: Verified parent agent delegation via `create_sub_agent`, child thread creation (`DBAnalyzer`), `subagent_start` event streaming, and synthesis back to the root turn.
   - Executed direct library turn via `@darex/workflows/dist/agent-client`: Verified full autonomous tool surface reporting and streaming in 11 seconds.
   - All 94 workflow tests passed (`pnpm --filter @darex/workflows test`).
