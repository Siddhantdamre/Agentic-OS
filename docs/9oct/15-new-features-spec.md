## 0. How to read this file

### 0.1 Why this list exists

Darex already has the hard parts most competitors lack: a multi-tenant kernel
with Postgres RLS, durable Temporal workflows, a plan-confirm-execute protocol,
an approval gate in the executor, ~154 chat tools across ~50 provider modules,
three memory stores (pgvector, Cognee, Hindsight), and specialised employees
with an Ask AI mode selector. What it lacks is the **surface area that users
now expect from any serious AI workspace**: attach a file, ask for research
with sources, get a document back, say "do this every Monday", talk to it on
the phone or WhatsApp, share a thread with a colleague, and trust a dashboard
that says how good and how expensive the employees are.

The test for inclusion: a feature is here only if (a) a buyer comparing Darex
with Lindy, Artisan, 11x, Sierra, Intercom Fin, Agentforce or a general AI
assistant would notice its absence, **and** (b) it fits the kernel without a
second runtime, a second OAuth broker or a second memory system of record
(`docs/plan/04-principles-and-constraints.md` §3).

### 0.2 Spec template

Every feature uses the same fields:

| Field | Meaning |

| **Success metric** | One primary metric and its target, plus guardrail metrics |

### 0.3 Invariants every feature inherits

These are not repeated in each spec; violating one is a bug.

1. **Tenancy.** Every new table has `org_id`, RLS, `WITH CHECK`; org comes from
   the session or the authenticated job context, never the body or model
   output (`AGENTS.md` §3 rule 1; `apps/dashboard/app/api/ask-ai/route.ts:432-435`
   refuses a body `org_id` today, and new routes do the same).
2. **Chat is the front door.** A feature is not done until it is reachable from
   `/chat` and has a row in `docs/new-109-pg-plan/gap26sept/chat-coverage.md`
   (generated by `services/workflows/src/scripts/chat-coverage.ts`).
3. **Risky actions park for approval.** New tools declare a risk class in
   `services/workflows/src/tools/risk.ts` and go through `tool-gate.ts`. Sends,
   payments, signatures, publishes and deletes are confirm-class.
4. **Honesty.** Disconnected or failed providers return `status:'error'`,
   `connected:false` and a setup URL; nothing is invented.
5. **Durability.** Anything that waits, repeats or spans more than one request
   is a Temporal workflow with idempotent activities.
6. **Traced and metered.** Every model call is traced to Langfuse
   (`services/workflows/src/langfuse-trace.ts`) and metered for billing.
7. **No new kernel frameworks.** CI's deny-list job (`.github/workflows/ci.yml:25-36`)
   blocks LangGraph, CrewAI, Letta, Mastra, Mem0 and similar.

## 1. Chat power — make the front door as capable as any AI workspace

### F01 · Web search and deep research with citations

**Problem.** Research is the most common "first question" a new user asks, and
it is where Darex is weakest. `web_search` fans out to Jina, SearXNG,
DuckDuckGo's HTML endpoint and Wikipedia (`tools/search-providers.ts:76,98,123,166`);
there is no paid search API, no result cache, no per-org quota, and no notion of
a multi-step research job. The 27 Sept audit (`docs/27sept-fable/14-web-research-and-search-capability.md`)
lists 52 findings, most still open: no numbered citations, no `fetchedAt`, no
"failed vs. nothing exists" distinction, extracted text entering the model
unfenced on one path, and answer post-processing that rewrote "could not find"
into invented facts (ASK-G09). Competitors ship cited deep research as a
default. Without it the Research employee is not credible.

**User story.** As a founder, I want to ask "compare the pricing of our three
biggest competitors and tell me where we are under-priced" and get a cited
report in a few minutes that I can open, edit and share, so that I stop doing
desk research by hand.

**UX.**
- Chat: a "Research" toggle next to the composer (also triggered by intent:
  "research", "compare", "find out"). Quick mode answers inline with numbered
  citations `[1]`; each citation chip opens the source with retrieved date.
- Deep mode shows a research plan card first (questions to answer, sources to
  try, estimated credits and time), uses the existing PlanCard approve flow,
  then streams progress ("read 14 of 30 sources") and lands an Artifact (F04)
  of type `research_report` with an executive summary, findings table,
  contradictions section and a full source list.
- "Save to Brain" button writes findings as `source: web` memories with URL
  and `fetchedAt` (opt-in, never automatic for third-party content).

**Backend design.**
- `services/workflows/src/tools/search-providers.ts`: add one paid provider
  behind an interface (Brave, Serper or Tavily; pick on price/quality bake-off),
  keep SearXNG as the self-hosted default and drop DuckDuckGo HTML scraping to
  last resort. Add a per-org token bucket using the existing
  `tools/provider-rate-limit.ts` and a 24 h result cache keyed on
  `(normalised query, locale)` in Redis (cache shared across orgs is safe for
  public web results; never cache tool results that carry org data).
- `tools/web-extract.ts`: add DNS-resolving SSRF check (the 27 Sept audit's
  rebinding finding), body size cap before `text()`, PDF support via the Docling
  path in `activities/ingest-file.ts:376`, return `{title, url, fetchedAt,
  truncated, contentHash}`.
- New `DeepResearchWorkflow` (Temporal): plan → parallel search per sub-question
  (bounded fan-out, max 6 concurrent) → extract top-k → per-source summarise
  with LiteLLM JSON (`apps/dashboard/lib/litellm-client.ts` pattern) → claim
  table with source ids → synthesis turn → critic check
  (`activities/critic-check.ts`) that every claim cites a source → artifact.
- Remove the answer rewriting in `tool-answer.ts` / `reply-from-tools.ts` that
  synthesised facts the tool did not return.
- Fence all extracted page text as untrusted (`services/workflows/src/untrusted.ts`)
  on both the in-process and bridge paths.
- Chat tools: `research_quick`, `research_deep_start` (plan-confirm), `research_status`.

**Data model.** `research_jobs (id, org_id, user_id, conversation_id, question,
plan jsonb, status, credits_est, credits_used, artifact_id, created_at)`;
`research_sources (id, org_id, job_id, url, title, fetched_at, content_hash,
used boolean)`. Migration range 211–212.

**Risks.** Cost blow-up (bound pages per job, show estimate first); prompt
injection from pages (fence + no tool calls allowed inside the research
workflow except search/extract); copyright (store excerpts, not full pages);
provider ToS for scraping (paid API removes the DDG risk of the platform IP
being banned for every tenant).

**Effort.** L (5 eng-weeks: provider + cache 1, extract hardening 1, workflow 2,
UI + artifact 1).

**Priority.** P0.

**Success metric.** ≥ 90% of research claims in a 50-question golden set carry
a resolvable citation that supports them (human-graded); median deep research
under 4 minutes; zero "invented fact" findings in the eval. Guardrails: cost per
deep job ≤ 20 credits (matches `payment-plans.md` §4.1 row 6); search provider
error rate < 2%.

### F02 · Attach files and images in chat (multimodal input)

**Problem.** The chat cannot take a file. The Ask AI route reads only `prompt`
and `conversationId` (`api/ask-ai/route.ts:436-443`); the Brain upload refuses
PDF/DOCX/XLSX (`api/brain/route.ts:537-544`). Yet a parser exists
(`activities/ingest-file.ts:376` Docling, `:417` `parseFile`) and WhatsApp media
can already be read (`apps/dashboard/lib/whatsapp-media.ts:20`). Users expect to
drop an invoice, a screenshot of an error, a contract or a price list into the
chat and ask about it.

**User story.** As an operations manager, I want to drop a supplier invoice PDF
into the chat and say "check this against the PO in Sheets and draft a reply if
it does not match", so that the employee works from the document I have in hand.

**UX.**
- Paperclip and drag-and-drop on the composer; paste an image from the
  clipboard. Chips show file name, pages, parse status.
- Per attachment: "Use for this chat only" (default) or "Also add to Brain".
- Images: the model sees the image; screenshots of dashboards and receipts work.
- Inbound channels (WhatsApp, email, widget) reuse the same pipeline, so a
  customer's photo of a damaged item reaches the Customer employee as an image.

**Backend design.**
- SP1 file store: `POST /api/files` (presigned upload, mime allowlist, 25 MB
  default, plan-tiered), `GET /api/files/:id` (scoped, short-lived URL).
- Ask AI route accepts `attachments: [{fileId}]`; resolves only files owned by
  the org and visible to the user; parse runs in a Temporal activity (never on
  the request thread) via the existing `parseFile`, results cached by content
  hash.
- Grounding: parsed text goes into the grounded user message
  (`buildGroundedUserMessage`, principle 10 in `04-principles-and-constraints.md`)
  with a token budget; long documents are chunked and retrieved per question
  instead of pasted whole.
- Images: LiteLLM model alias `darex-vision` (new entry in
  `infra/litellm/config.yaml`), passed as image parts; OCR fallback through
  Docling for scanned PDFs.
- New chat tools: `file_read` (text of an attached file by id, page range),
  `file_list` (files in this conversation/project).

**Data model.** `org_files (id, org_id, uploaded_by, storage_key, name, mime,
size_bytes, sha256, scan_status, parse_status, parsed_text_ref, created_at,
deleted_at)`; `conversation_files (org_id, conversation_id, file_id)`. DSR:
add `org_files` to `CUSTOMER_DATA_TABLES` in `services/workflows/src/dsr/tables.ts`
and delete objects in the purge saga.

**Risks.** Malware (real scanner, ClamAV container, before parse); PII in files
reaching the model provider (existing redaction `activities/redact.ts` applied
before embed; disclose in DPA); cost of vision tokens (meter separately); a
file id from another org (RLS plus explicit join on `org_id`).

**Effort.** M (3 eng-weeks including SP1).

**Priority.** P0.

**Success metric.** ≥ 30% of weekly active chat users attach a file within 60
days of launch; parse success ≥ 97% on the supported types; p95 time from
upload to "ready" < 20 s for a 20-page PDF.

### F03 · Data analysis on spreadsheets and databases

**Problem.** Owners ask numeric questions ("which salesperson has the worst
response time this month", "plot weekly revenue from this CSV"). Today the
agent can read a sheet (`tools/google-sheets.ts` `sheets_read`), run a
read-only query (`tools/database.ts`) and run code in a sandbox
(`tools/sandbox.ts:15`, confirm-class), but there is no analysis loop that
loads a file into the sandbox, iterates on pandas/SQL, and returns a chart and
a table. Every answer is prose.

**User story.** As a sales head, I want to upload last quarter's pipeline
export and ask "where are deals stalling and by how much", and get a chart, a
table and three findings I can paste into a deck.

**UX.** In chat, an "Analysis" block shows the steps (load → clean → compute),
collapsible code, the resulting table (sortable) and a chart; "Open as
artifact" turns it into an F04 sheet or chart artifact; "Re-run with this
month's data" schedules it (F06).

**Backend design.**
- Sandbox image (`infra/docker/sandbox/`) gets pandas, duckdb, matplotlib/vega
  export; no network inside the sandbox; files mounted read-only from SP1 under
  an org-scoped path.
- New `analysis_run` tool: input = file ids or a connected source + question;
  runs an internal loop of up to N code cells in the sandbox with output
  captured; returns tables (≤ 1k rows), a Vega-Lite chart spec, and the code.
- Read-only analysis (no writes, no network) can be marked `read` risk with a
  separate sandbox profile so it does not need approval each time; the general
  `code_execution` keeps confirm-class.
- Connected-source mode: query via `database_query` / `sheets_read`, then hand
  results to the sandbox as a parquet file.

**Data model.** Reuses SP2 (`artifacts` with `kind = 'table' | 'chart'`) and
`analysis_runs (id, org_id, conversation_id, inputs jsonb, code text,
status, duration_ms, artifact_id)`.

**Risks.** Sandbox escape (no network, CPU/mem/time limits, separate profile);
wrong numbers presented confidently (show the code, row counts and filters
used; critic check that numbers in prose match the table); large files (cap
rows, sample with disclosure).

**Effort.** L (4 eng-weeks).

**Priority.** P1.

**Success metric.** Golden set of 40 analysis questions over fixture files:
≥ 90% numerically correct. Adoption: ≥ 15% of active orgs run an analysis
monthly.

### F04 · Darex Artifacts: generated docs, sheets, slides and charts

**Problem.** Darex can create Google Docs, Sheets and Slides
(`tools/google-docs.ts:199`, `tools/google-sheets.ts:127`,
`tools/google-slides.ts:285`), but only in the customer's Google account, only
when connected, and the result is a link. There is no native, versioned output
the user can edit in place, comment on, regenerate a section of, or export as
PDF/DOCX/PPTX. Proposals, reports, SOPs, briefs and research all end up as long
chat messages.

**User story.** As a founder, I want to say "turn this thread into a one-page
proposal for Acme" and get a document beside the chat that I can edit, ask the
employee to revise a section of, and export to PDF or push to Google Docs.

**UX.**
- Split view: chat on the left, artifact on the right (mobile: full-screen
  tab). Types: document (rich text), table/sheet, slide deck, chart, research
  report, email draft.
- Inline "Ask to revise" on a selection; version history with diff and restore.
- Export: PDF, DOCX, PPTX, CSV; "Publish to Google Docs/Sheets/Slides" uses the
  existing tools (confirm-class only when sharing externally).
- Artifacts are listed in a Library tab and referenced by `@artifact` in chat.

**Backend design.**
- SP2 artifact store with typed JSON content. Rendering in `NEW-FRONTEND`
  (TipTap or Lexical for docs, a lightweight grid for tables, a slide renderer
  from a constrained JSON schema). Exports rendered server-side in a worker
  activity (headless Chromium for PDF; `docx`/`pptxgenjs` libraries).
- Chat tools: `artifact_create`, `artifact_update` (section patch, not full
  rewrite), `artifact_get`, `artifact_export`, `artifact_publish_google`.
- Revisions reuse the draft revision route pattern
  (`apps/dashboard/app/api/ask-ai/revise/route.ts`) and keep a human-first rule:
  a revision is a new version, never an overwrite.
- Memory: artifacts are not auto-embedded; "Add to Brain" is explicit.

**Data model.** `artifacts (id, org_id, created_by, conversation_id, project_id,
kind, title, current_version, visibility, created_at, updated_at)`;
`artifact_versions (id, org_id, artifact_id, version, content jsonb,
author_kind ('user'|'employee'), author_id, change_note, created_at)`;
`artifact_citations (org_id, artifact_version_id, source_kind, source_ref)`.

**Risks.** Export library vulnerabilities (pin, run in worker not dashboard);
large artifacts in Postgres (move content > 1 MB to SP1); confusion with
Google-native docs (clear "Darex copy vs Google copy" labelling).

**Effort.** L (6 eng-weeks; frontend-heavy).

**Priority.** P0 (documents) / P1 (slides, charts).

**Success metric.** ≥ 40% of weekly active users open or create an artifact
weekly by day 90; ≥ 25% of artifacts exported or published; revision requests
per artifact median ≤ 2 (quality signal).

### F05 · Projects: persistent chat workspaces with pinned context

**Problem.** Ask AI threads are flat and per user (`api/ask-ai/route.ts:175-192`).
History is capped at the last 12 messages, 2,000 characters each
(`route.ts:453-466`). There is no place to keep "everything about the Acme deal"
or "Q4 hiring" with standing instructions, files and artifacts that every
thread in it inherits.

**User story.** As an account manager, I want a project for each key account
with pinned files, instructions ("always CC the AE") and a default employee,
so that every new chat about that account starts with the right context.

**UX.** Left rail lists Projects; each has instructions, pinned files (SP1),
pinned artifacts (F04), linked CRM entity, default Ask mode (Auto / Pick one /
Team), members (F19). Starting a chat inside a project shows a context chip.

**Backend design.** Project context is injected into the grounded user message
with a budget; pinned files go through retrieval, not paste. Memory retrieval
(`services/workflows/src/memory/retrieve.ts`) gains an optional `project_id`
boost. Ask mode validation (`apps/dashboard/lib/ask-mode.ts`) reads the project
default when the conversation has none. Chat tools: `project_list`,
`project_add_note`.

**Data model.** `projects (id, org_id, name, instructions, default_ask_mode,
default_employee_ids uuid[], crm_entity_ref, created_by, archived_at)`;

### F06 · Scheduled and recurring tasks from chat

**Problem.** Users say "every Monday at 9 send me a pipeline summary" or
"remind the team on the 1st to submit expenses". Darex has 14 system sweeps in
a fixed list (`periodic-registry.ts:33-53`) and an `OwnerBriefingWorkflow`, but a
user cannot create, list, pause or delete their own schedule. This is table
stakes in Lindy, Zapier Agents and general assistants.

**User story.** As a founder, I want to type "every weekday at 8:30 send me
yesterday's new leads and unanswered customer messages on WhatsApp" and have it
just happen, and say "stop the morning lead summary" to end it.

**UX.**
- Chat detects scheduling intent and shows a Schedule card: plain-English
  recurrence ("Every weekday at 08:30 Asia/Kolkata"), the task prompt, the
  employee, delivery channel, the next three run times, credits per run.
  Approve to create.
- Settings → Schedules lists all schedules with owner, last run, last result,
  next run, pause/resume/delete, "run now".
- Each run creates a thread entry (or an artifact for reports) and a
  notification via SP5.

**Backend design.**
- SP3: `user_schedules` table; creation calls Temporal's Schedules API
  (`client.schedule.create`) with id `sched:<org_id>:<schedule_id>`, spec built
  from a parsed RRULE-like structure, timezone from `org_onboarding.timezone`
  (`027_onboarding_cold_start.sql:6`) or a user override.
- Each tick starts `ScheduledTaskWorkflow` → `runAgentTurnActivity` (already
  guarded against duplicate retries, see `BUILD_STATE.md` 2026-10-05 "A retried
  agent turn…") with the stored prompt, the creator as actor, and the
  employee's allowlist. Sends inside a scheduled run follow the same tool gate;
  a schedule can be granted "pre-approved send to me only" (recipient pinned to
  the creator) so self-digests do not need daily approval.
- Recurrence parsing: LiteLLM JSON extraction plus a deterministic validator
  (minimum interval 15 minutes on paid plans, 1 day on Free; max 50 schedules
  per org on Growth). Respect quiet hours (`services/workflows/src/quiet-hours.ts`).
- Chat tools: `schedule_create` (confirm), `schedule_list`, `schedule_pause`,
  `schedule_delete` (confirm), `schedule_run_now`.
- Plan entitlements: `payment-plans.md` §3 ("1 Daily Run" Starter, hourly on
  Growth) enforced at create time.

**Data model.** `user_schedules (id, org_id, created_by, employee_id, title,
prompt, recurrence jsonb, timezone, delivery jsonb, preapproved_self_send bool,
status ('active'|'paused'|'deleted'), temporal_schedule_id, last_run_at,
last_status, next_run_at, created_at)`; `schedule_runs (id, org_id,
schedule_id, workflow_id, started_at, finished_at, status, credits, output_ref)`.

**Risks.** Runaway cost (credit estimate shown at creation, per-schedule
monthly cap, auto-pause after 3 consecutive failures); orphan Temporal
schedules after org deletion (purge saga deletes them; reconciliation sweep
compares table vs. Temporal); a schedule created by a user who later leaves
(re-own to an admin on member removal).

**Effort.** M (3 eng-weeks).

**Priority.** P0.

**Success metric.** ≥ 40% of active orgs have at least one user schedule by
day 60; ≥ 98% of scheduled runs start within 2 minutes of due time; auto-pause
rate < 5%.

### F07 · Standing orders: event-triggered automations from chat

**Problem.** "When a new lead from the website mentions 'enterprise', assign it
to Priya and draft a reply" is an event rule, not a schedule. Today such logic
is hard-coded in employee engines (`services/workflows/src/{growth,customer,operations}`)

**User story.** As a sales ops lead, I want to tell the Sales employee "whenever

**UX.** A Rule card in chat ("When … If … Then …", with a sample of the last 5
events that would have matched), approve to activate; Settings → Automations

run timeline (F33).

**Backend design.** SP4 trigger bus: normalise inbound messages, `work_events`,
connector webhooks (HubSpot, Stripe, Gmail push) and internal events into an

conditions only — field, operator, value — compiled from natural language by

**Data model.** `automation_rules (id, org_id, created_by, employee_id, name,

allowlist); silent breakage when a connector disconnects (rule shows "paused:
HubSpot disconnected").

**Effort.** L (5 eng-weeks).

**Priority.** P1.

**Success metric.** ≥ 25% of Growth-plan orgs run ≥ 1 custom rule by Q1 2027;
false-fire rate < 2% (human-flagged); zero loop incidents.

**Success metric.** Support tickets "why did the AI do X" resolved in-product ≥
70%.

### F34 · Dry-run and simulation mode

**Problem.** The Free plan promises "plan-confirm-execute runs in simulated
sandbox mode; no external system mutations" (`payment-plans.md` §3.1), and new
employees, rules and recipes need a safe test. No dry-run mode exists in the
executor.

**User story.** As a cautious owner, I want to run the new collections employee
against last month's data and see exactly which emails it would have sent,
without sending any.

**UX.** "Test run" on employees, rules, recipes and schedules; results show
would-be actions with full previews; Free-plan orgs see the same view for every
plan.

**Backend design.** A `dryRun` flag on `ToolActionContext`: read tools execute
normally; write/send/pay/sign tools return a synthetic "would do" result
derived only from their arguments (clearly marked, never stored as real), so
nothing is fabricated about the outside world. Replay mode feeds historical
events from SP4 into rules/recipes.

**Data model.** `simulation_runs (id, org_id, target_kind, target_id, window,
results jsonb)`.

**Risks.** A dry-run flag that leaks into a real run (flag set only by the
simulation workflow; executor refuses side effects when set; test asserts
every write tool honours it — same pattern as the chat-coverage test).

**Effort.** M (2 eng-weeks). **Priority.** P1.

**Success metric.** ≥ 60% of new rules/recipes are test-run before activation;
Free-to-paid conversion lift measured against cohort before launch.

### F35 · Ask your data: governed natural-language analytics

**Problem.** `database_query` is read-only SQL over the Darex database
(`tools/database.ts`) and the metrics registry answers a fixed set of ids;
chat once failed a basic count question until the agent was told to use SQL
(`BUILD_STATE.md` 2026-09-30). Customers want the same over their own
warehouse/Postgres and connected SaaS data, with consistent definitions.

**User story.** As a COO, I want to ask "revenue by city last quarter vs. the
one before" over our Postgres and get a correct table with the SQL shown.

**UX.** Same as F03 output; a "definitions" panel listing metrics used.

**Backend design.** Customer DB connector (read-only role, network via
customer-provided tunnel), a semantic layer (YAML metric definitions per org,
extending `tools/metrics.ts`), SQL generation constrained to the semantic
layer, `EXPLAIN` cost check and row limits, results to F03.

**Data model.** `data_sources (id, org_id, kind, conn_sealed, status)`;
`semantic_metrics (id, org_id, name, sql_template, dimensions)`.

**Risks.** Wrong joins (semantic layer only, show SQL); load on customer DB
(timeouts, read replica recommended).

**Effort.** L (5 eng-weeks). **Priority.** P2.

**Success metric.** ≥ 90% accuracy on a customer-provided 30-question set
before go-live per org.

## 9. Growth and enterprise

### F36 · Ten-minute onboarding: seed the Brain from what already exists

**Problem.** Time to first cited answer is the Free pilot's stated goal
(< 10 minutes, `payment-plans.md` §3.1). Today a new org has an empty Brain
until someone connects Drive and waits for ingest, or pastes text (binary
upload refused, `api/brain/route.ts:537`). First impressions are generic
answers.

**User story.** As a new signup, I want to enter my website and connect Gmail,
and within minutes ask "what do we sell and to whom?" and get an answer cited
from my own site and emails.

**UX.** Onboarding step "Teach Darex about your business": website URL (crawl
up to 50 pages via `web_extract`), connect Gmail/Drive (last 90 days, opt-in
labels/folders), upload files (F02); live progress; a generated "Company
profile" artifact to confirm or correct; three suggested first tasks per
business type.

**Backend design.** `OnboardingSeedWorkflow`: crawl → extract → embed through
the existing ingest/embed path (`IngestWorkflow`, `EmbedWorkflow`); company
profile via LiteLLM JSON with citations; confirmed fields become verified facts
(F23); uses `onboarding-rollout.ts` hooks.

**Data model.** `org_onboarding` add `seed_status`, `profile_artifact_id`.

**Risks.** Crawling sites the user does not own (domain must match the signup
email domain or be verified); ingesting private email without consent
(explicit label/folder selection).

**Effort.** M (2 eng-weeks). **Priority.** P0.

**Success metric.** Median time from signup to first cited answer < 10
minutes; Free → paid conversion up ≥ 20% vs. prior cohort.

### F37 · Enterprise trust pack: SCIM, residency, retention and audit export

**Problem.** SSO routes exist but the test-IdP proof is open (S7); there is no
SCIM, no retention policy, no audit export to a SIEM, and data residency is
"design only" (`docs/plan/README.md` §Not started). Enterprise tier promises
SSO/SAML, SOC 2 logs, residency and a zero-training rider (`payment-plans.md`
§3.1 tier 5).

**User story.** As an IT admin at a 500-person company, I want users
provisioned and removed from Okta/Entra, chat retention set to 180 days, audit
events streamed to our SIEM, and our data kept in India.

**UX.** Enterprise settings: SSO (test connection), SCIM token, retention per
data class, audit export (S3/webhook/syslog), region shown read-only.

**Backend design.** SCIM 2.0 endpoints mapping to users/memberships with
`session_epoch` bump on deprovision (existing in `lib/session-epoch.ts`);
`RetentionWorkflow` deleting by data class with DSR-table coverage reuse
(`dsr/tables.ts`); audit export worker; residency as a **deployment** (separate
regional stack per region with routing at signup), not row-level tagging.

**Data model.** `retention_policies (org_id, data_class, days)`;
`audit_exports (org_id, kind, target_sealed, cursor)`; `orgs.region`.

**Risks.** Retention deleting legal-hold data (legal hold flag overrides);
regional stacks doubling ops (only on signed demand).

**Effort.** XL (7 eng-weeks; residency extra). **Priority.** P1.

**Success metric.** First enterprise security review passed without open
critical items; SCIM deprovision effective < 5 minutes.
