## 1. Executive summary

**Where we are.** Darex has a real kernel: multi-tenant Postgres with RLS and a
CI isolation suite, Temporal workflows (27 workflow files plus 14 per-org
sweeps), a plan-confirm-execute chat with an approval gate in the executor,
~154 chat tools, three specialised employee engines plus a roster with an Ask
mode selector (Auto / Pick one / Team), Nango OAuth, LiteLLM, three memory
stores, Langfuse tracing on both dashboard and worker, Stripe/Razorpay billing,
DSR, a platform console, and a one-command deploy to a shared Azure VM. Most
P0/P1 rows of the 26 Sept gap audit are closed in code.

**What is missing is proof and surface.** Proof: every one of the 238 rows in
the chat-coverage matrix is still 🔴 (none proved live from `/ask-ai`), the
eval suites are not run in CI, many recent fixes say "not verified against a
live stack", provider OAuth IDs are human-blocked, and production is a single
shared VM without zero-downtime deploys. Surface: no file attachments, no cited
deep research, no artifacts, no user schedules, no shared threads, WhatsApp for
owners only understands four commands, no PWA, no public API, no voice.

**The plan in one line per horizon.**

| Horizon | Window | Theme | Headline outcome |
|---|---|---|---|
| Now | 2026-10-09 → 10-23 | Prove and stabilise | Evals in CI, chat-coverage proving started, open P1 fixes closed, staging stack up |
| 30 days | → 2026-11-08 | Chat that does real work | Attachments, cited research (quick), schedules, owner WhatsApp Ask, cost ledger |
| 60 days | → 2026-12-08 | Team and trust | Shared threads, approvals inbox 2.0, PWA push, artifacts (docs), deep research, budgets |
| 90 days | → 2027-01-07 | Paid launch ready | Ten-minute onboarding, quality dashboard, standing orders, Slack front door, GA checklist met |
| Q1 2027 | 2027-01 → 03 | Learning and reach | SOP learning, proactive insights, Brain 2.0, Hindi + multilingual, public API, MCP server, voice inbound beta |
| Q2 2027 | 2027-04 → 06 | Platform and scale | Workflow builder, voice outbound, template gallery, enterprise trust pack, agency mode (gated), multi-node prod |

**What we will not build** in this window is as important as what we will
(section 12): no native mobile apps, no second runtime, no free-form canvas, no
public skill store, no Wave 4 verticals, no browser agent unless three paying
customers ask.

### 2.4 Competitive context (why the feature list)

`competitors/competitor-analysis.md` ranks 11x, Artisan, Lindy, Agentforce,
Sierra, Decagon, Intercom Fin and others. Darex's defensible ground is the
combination of cross-function employees, real tool execution with approvals,
a shared Brain, and WhatsApp-first India GTM at SMB prices. The gaps a buyer
notices first in a demo are generic: "can I upload a file", "can it research
with sources", "can it do this every Monday", "can my team see this", "can I
approve from my phone", "how good is it and what will it cost". The 30/60/90
plan closes exactly those first; differentiators (voice, learning, builder,
agency) follow once the basics are proven.

## 3. Sequencing principles

1. **Prove before we add.** A horizon cannot close while its fixes are
   unverified. "Built" means merged; "done" means the milestone's DoD is met on
   staging with real accounts where the feature touches a provider.
2. **Shared primitives before features.** SP1 file store, SP2 artifact store,
   SP3 schedule service, SP5 notification service and SP7 quality/cost ledger
   come first because 3–7 features each depend on them (spec §0.6).
3. **Extract `askAiTurn()` early.** `apps/dashboard/app/api/ask-ai/route.ts`
   is 1,571 lines and is the only path to the full chat brain. WhatsApp, email,
   Slack, the public API and the MCP server all need it as a callable module.
   Doing this once in the first 30 days prevents five forks.
4. **Chat first, tab second.** Every feature lands as chat tools plus a
   chat-coverage row before any dedicated tab UI.
5. **One concern per release train.** Weekly releases; each feature behind an
   org feature flag (`apps/dashboard/lib/org-feature-flags.ts`) and rolled out
   design partners → 25% → all.
6. **Revenue-relevant first.** Order inside a horizon by (a) blocks paid launch,
   (b) shows in the first demo, (c) differentiates, (d) internal efficiency.
7. **Human-blocked items get owners and dates, not workarounds.** OAuth IDs,
   keys and licences are tracked in section 9.3 and never faked.
8. **The kernel stays.** No new agent runtime, memory SoR, OAuth broker or
   workflow engine (`docs/plan/04-principles-and-constraints.md` §3; CI
   deny-list).

## 11. Operating cadence

### 11.1 Weekly

- Monday: plan the week from this roadmap's current horizon; pick fixes from
  the 20% budget.
- Wednesday: design-partner call rotation (two partners a week).
- Friday: release train to production behind flags; `BUILD_STATE.md` entries
  checked; KPI report reviewed.

### 11.2 Budget rule

Each engineer-week: 70% horizon features, 20% fixes and proving, 10%
unplanned (incidents, support). If unplanned exceeds 25% for two weeks in a
row, the next horizon is re-cut, not stretched.

### 11.3 Definition of done for any roadmap item

A roadmap item is done only when all of the following hold (combines
`docs/plan/04-principles-and-constraints.md` §9 and the blueprint's 7-point
DoD in `plan/06_gap_analysis_and_what_is_missing.md` §5):

1. Works for two orgs without leakage (RLS test for every new table).
2. Honest when disconnected or failing; nothing fabricated.
3. Risky actions park for approval; timeouts never approve.
4. Webhooks ACK first, work in Temporal.
5. Traced in Langfuse and metered in the credit ledger.
6. Model output validated by schema where structured.
7. Eval or check script for user-facing agent behaviour; unit tests for logic.
8. Reachable from chat with a chat-coverage row proved 🟢.
9. Feature flag, rollout note, and `BUILD_STATE.md` entry in the same commit;
   matching `gap26sept/` or this roadmap's row updated.
10. Verified on staging with real provider accounts where a provider is
    involved; "not verified" lines are allowed only with a named reason.

### 11.4 Roadmap maintenance

- This file is updated at each milestone review (M0…M7) with a dated
  "Changes" note at the bottom; dates move only with a reason.
- Status of features lives in `15-new-features-spec.md` §0.5 (add a Status
  column when the first one ships).
- Disagreement between this file and code: code wins on what exists; this
  file wins on what to build next until `BUILD_STATE.md` records a deviation.

## 12. What NOT to build (and why)

| Do not build | Why | Revisit when |
|---|---|---|
| A second agent runtime or orchestration framework (LangGraph, CrewAI, Mastra, Letta) | Dual runtimes double bugs and security surface; CI deny-list exists for this reason | Never as kernel |

| A public, anonymous template/skill store | Unreviewed templates can act on customer systems | Curated partner program proves safe |
| Cross-org learning from customer data | Trust and legal; per-org learning only | Never without explicit opt-in program and legal sign-off |
| Our own foundation model or fine-tunes | Cost, no data rights; routing + evals give the gains | Never in this window |
| Outcome-based pricing (per resolution) | Needs mature attribution; credits are the 2027 model | After 2 quarters of clean SP7 data |
| Every connector in the catalog | Spray creates dead tiles; finish credentials for the top 10 first | Per-connector demand from ≥ 3 paying orgs |
| Wave 3–4 vertical packs (clinics with PHI, education with minors, insurance) | Compliance cost; `docs/plan/phases/04-phase-complete.md` §3 | RFC + compliance review + paying demand |

## Appendix C · Milestone demo scripts

using real accounts. A milestone does not close if the demo needs a workaround.

outreach to Support; show the eval gate failing it. Show the chat-coverage file
with 60+ green rows and click a trace id.

delivery note, ask "do these match?"; ask "research the top three competitors'
pricing"; say "every weekday at 8:30 send me unanswered WhatsApp messages";
from a phone, send the owner WhatsApp number "what happened with the Sharma
lead?" and approve a plan with a button. Open the usage tab and show credits
for each of these.

refund step; B gets a push on the PWA and approves with fingerprint. An admin
policy auto-approves a ₹1,500 refund and refuses ₹15,000. "Turn this thread
into a proposal for Acme" → artifact → revise section 2 → export PDF. Start a
deep research job and open the report.

**M3 demo (Jan 7).** Fresh signup with a new work email → verify → website +
Gmail seed → cited answer about the business in < 10 minutes. `@Darex` in
Slack asks Finance for last month's ad spend. A HubSpot deal moving to
Negotiation fires a standing order once. Quality tab shows each employee's
score and a failure with a trace.

**M4 demo (Feb 15).** Show five edits teaching a reply-style rule, the rule
proposal with evidence, the eval delta, acceptance, and the next draft using
it. An anomaly alert on response-time spike with a one-click plan.

**M5 demo (Mar 31).** Hindi UI walkthrough; a Hinglish WhatsApp customer
answered in Hinglish. A Python script using the SDK creates a task and receives
the webhook. An external MCP client asks for pending approvals. A live inbound
call books a site visit and posts a summary to WhatsApp.

**M6 demo (May 15).** Describe a client onboarding process in chat → recipe →
edit a step → dry-run → publish → run for a new client. Install a gallery
template. Outbound callback to a consented lead.

**M7 demo (Jun 30).** Deprovision a user in a test IdP via SCIM and show the
session ending. Retention job on a test org. Rolling deploy with zero failed
