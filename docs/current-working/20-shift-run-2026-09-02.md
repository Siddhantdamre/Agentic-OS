# 20 — The first real shift run, 2 September 2026

Date: **Wednesday 2 September 2026**, evening (IST).

A record of the first time every AI employee in a workspace did its own job
without being asked, what broke on the way, and the exact evidence. Written
from the Temporal workflow results and the container logs, not from memory.

Callers: indexed from [README.md](./README.md). Not imported by application
code. No data files.

---

## What was being tested

Six employees in *Sharma Properties, Thane* each hold a standing duty
(`services/workflows/src/duties.ts`) dispatched through
`AutonomousAgentWorkflow` — the same engine that answers a customer message.
The question was not "does the code run" but **"does each employee produce work
a broker would recognise as its job?"**

Three runs were needed. Each failed differently, and each failure was real.

### Three defects, in order of severity

**1. A model group with no fallback.** LiteLLM logged it exactly:

```
Upstream error from Nvidia: Service temporarily overloaded
No fallback model group found for original model_group=atomic-agent-deepseek
Fallbacks=[{'atomic-agent': [...]}]
```

The fallback chain covered `atomic-agent` only, on the assumption written at
the top of `infra/litellm/config.yaml`: *"the atomic-agent always calls model
atomic-agent; LiteLLM owns failover."* That assumption is false. The per-tenant
budget gate pins an over-budget workspace straight to the zero-cost tier via
`modelOverride`, so the request arrives as `atomic-agent-deepseek` and never
passes the front door. **The one tier the budget gate depends on was the one
tier with nowhere to fall.**

Fixed by giving every group a chain, with the budget intent preserved: a
zero-cost tier falls only to the *other* zero-cost tier — different provider,
separate balance — never onto a paid one, because that would bill exactly the
workspace the gate was protecting the account from.

Guard: `check-model-fallbacks.js`, 6/6, registered in `verify.js`.

**2. Silence recorded as success.** `AutonomousAgentWorkflow` passed the
activity's verdict through untouched, so an agent that used no tool and said
nothing returned `success: true`. An operator sees a green tick under an
employee that did not do its job. ADR 3 says silence is never recorded as
success; that was enforced on the customer reply path in `WorkItemWorkflow` and
not here, so Ask AI and every shift inherited the hole.

**3. Two duties I wrote were undoable.** The Buyer ISA duty asked for
"conversations with no recorded qualification" — there is no qualification
field in the schema, so the agent could not form a query and correctly produced
nothing. The Research duty referenced a watchlist that nothing supplies. Both
now name real columns and real URLs.

## What this run proves, and what it does not

**Proves:**

- Each employee performs work specific to its role, using only the tool its
  duty needs — Sarah holds gmail and whatsapp; her duty ran with
  `database_query` alone
- The agent reaches the open internet with no credential (the reader endpoint
  answers unauthenticated), so "source-backed" is not aspirational
- Two independent paths agree on the same number, which is what makes the
  dashboard trustworthy rather than merely populated
- The permission model distinguishes *not permitted* from *not connected*, and
  reports which

**Does not prove:**

- Answer quality. These are structured lookups, not judgement calls. The four
  suites that measure quality still need model credit and have never run.
- Anything about a real customer. The workspace is seeded; the "12 days"
  contact is synthetic.
- The briefing panel's rendering. It is compiled into both server and client
  bundles and `/api/briefings` returns 401 unauthenticated, so it exists and
  enforces auth — but nobody has looked at it.

## My own errors this session, recorded

Kept because the pattern matters more than the individual mistakes.

- **Claimed 6 of 8 employees could work today**, reading the table off the duty
  definitions instead of the real roster. The planner said 2. Four employees did
  not hold `database_query` at all.
- **Reported Priya at 48 actions.** Real figure 6 — my query LEFT JOINed actions
  *and* conversations, giving 6 × 8.
- **Called 52 duplicate "Sarah" rows one org.** They are 52 separate orgs, each
  named "Bright Leaf Interiors" with one employee.
- **Wrote a checker with two bugs of its own**, and both produced confident
  false failures about correct config: `\b` matched mid-name because
  `atomic-agent` is a prefix of `atomic-agent-fallback`, and a `:free` marker
  matched the *comment* "Both fallbacks were :free models" and classified the
  paid tier as free.
- **Dispatched the first shift to `darex-tasks`.** The worker polls
  `darex-agent-tasks`; I invented the name. The workflows sat at
  `historyLength: 2`, RUNNING and never picked up, with no error anywhere.
- **Read `rc=0` from a piped command** and concluded Docker was healthy. That
  was `head`'s exit code. Docker was hanging.

The through-line: every one of these was caught by running the thing rather
than reasoning about it, and four of them were caught by a check disagreeing
with me.

## Operational notes added by this run

- **A Docker build needs no containers.** The Next.js production build dies with
  `failed to receive status: rpc error … EOF` when the stack is running.
  `docker compose stop` the non-essentials, build, then bring them back. This
  worked where four consecutive attempts had failed.
- **TypeScript needs `NODE_OPTIONS=--max-old-space-size=4096`** on this machine,
  or it exits with `FATAL ERROR: Zone Allocation failed - process out of memory`.
- **Do not run Node and a Docker build at once.** A shift-planner run during a
  build crashed with a native stack trace.
- **`node --test` on a repo-relative path fails inside a container** unless the
  script sits where `node_modules` resolves; `node -e` from the working
  directory does not have that problem.
- **After a Docker restart the port proxy is unreliable.** `docker compose
  restart postgres` re-establishes it. Running work inside a container avoids
  the proxy entirely and is the more reliable path.
