## The headline

**The agents could not search the web, and had never been able to.**

`web_search` called `s.jina.ai`, which returns 401 without `JINA_API_KEY`. That key has
never been set in this deployment. An agent could *read* a page somebody named — the
reader endpoint answers keyless — and could never *find* one.

Five separate places carried that dependency, which is why nobody owned it:

| Where | What it did |
|---|---|
| `tools/web-search.ts` | returned `web_search requires JINA_API_KEY` |
| `activities/market-research.ts` | `if (!jinaKey) return []` — every research run silently empty |
| `duties.ts` `KEY_GATED` | reported `web_search` as "not connected" for every employee |
| `mcp-bridge.ts` | told the model "Requires JINA_API_KEY" |
| `api/ask-ai/route.ts` | computed `available: jinaKey`, correctly telling the agent it could not search |

Now one function, four providers, and a floor that needs no credential — see
[ADR 20](../adr/020-search-has-a-keyless-floor.md).

Two defects were found by running it against real questions rather than a smoke test:

- **DuckDuckGo throttles bursts.** Three queries back to back failed; the same query alone
  returned four results. Backs off twice now, and distinguishes "no result markup"
  (throttled, transient) from "markup present, nothing extracted" (`PARSER STALE` —
  permanent, and the reason a dead parser reads as "the internet had nothing on that").
- **Wikipedia never says no.** It answered "Maharashtra ready reckoner rate hike 2026"
  with **"One Rank, One Pension"**. Real title, real URL, real snippet, and an agent would
  have cited it. The first relevance rule required one matching term, and it then answered
  "best CRM for Indian real estate brokers" with Cognizant, IBM and a list of unicorn
  startups — all matching on "Indian". The bar now scales with query specificity.

### Deep research

A new capability, not a rename. `deep-research.ts` plans a bounded loop: search, read the
**pages** rather than the snippets, ask what is still missing, search for that.

Follow-up queries come from the open questions synthesis produced, never from permuting
the topic — permutation returns the same page four times, which then reads as four-way
corroboration.

Every run records why it stopped and says so at the top: `answered`, `exhausted`,
`no-progress` or `budget`. No open questions on a one-publisher evidence base reports
`exhausted`, not `answered` — an empty gap list from a thin run is an incurious model, not
a settled question.

Validation goes through the existing `validateFindings`, shared with the single-shot path,
so *deeper* can never come to mean *less strict*.

Registered as a **tool**, not only a workflow. `MarketResearchWorkflow` was exported and
started by nothing; a capability an agent cannot choose to invoke runs only when a human
remembers it exists.

## The gate had never run on this machine

`verify.js` launches every suite with `process.execPath` and passed
`shell: process.platform === 'win32'` unconditionally. With `shell: true` Node joins the
binary and its arguments into one string for `cmd.exe` **without quoting**, so node's
default Windows install path — which contains a space — arrives as the command
`C:\Program`.

Every node-launched suite died with `'C:\Program' is not recognized`. The verdict was:

```
NOT SOUND — 23 of 23 suites failed.
```

Not one was a code failure. All of them pass when run by hand.

The deeper defect underneath it: **a suite that could not start was reported identically to
a suite that ran and failed.** They need opposite responses — fix the code versus fix the
machine — and collapsing them is exactly how the quoting bug survived, presenting as a
total product failure in the loudest available terms.

The same shape appeared in the push gate the same day. It refused a push with
`typecheck fails` and an *empty* detail, while `tsc --noEmit` passed by hand: `npx` is
broken on this machine (npm's launcher resolves a doubled path), it writes to stderr, and
the check read only stdout. A gate that blocks for an unexplainable reason gets routed
around with `--no-verify`, which is strictly worse than no gate.

**Measured, same machine, same commit:**

| | verdict |
|---|---|
| before | `NOT SOUND — 23 of 23 suites failed` |
| after (`--fast`) | `INCOMPLETE — 22 of 24 passed; 2 could not run; nothing failed` |
| after (full stack) | **62 of 64 passed, 2 could not run, none failed** |

The two are `typecheck` and `lint`, which need pnpm. pnpm is not installed here, and
routing through corepack does not help — `typecheck:ci` invokes `pnpm --filter` internally
per workspace and turbo shells out to the package manager itself. Both now report one
actionable line: `corepack enable pnpm`.

## Supervision covered one workflow of sixteen

ADR 8 says supervision is recorded on every exit. `lint-supervision-coverage.js` opens
with "EVERY EXIT IS SUPERVISED — enforced structurally, not remembered" and passes 6 of 6.

It reads `WorkItemWorkflow.ts`. Only that. Its path is hardcoded.

Live database: **807 rows in `agent_actions`, one row in `task_supervision`**, written on
31 August. The fifteen workflows that record nothing include `AutonomousAgentWorkflow` —
what every standing duty and every inbound customer reply runs through.

The defect was never that fifteen are unsupervised. Some correctly are: an embedding job
has no doer to monitor. It is that nothing recorded **which**, so a deliberate exclusion
and an oversight were indistinguishable, and the lint's own name asserted the opposite.

Every workflow now supervises or states its case in writing — the bargain
`lint-check-coverage.js` already makes for checkers. Silent fails the build; a declared
`GAP` prints every run with its reason and a count.

| | workflows |
|---|---|
| supervised | WorkItem |
| excused (5) | Embed, Ingest, Sync, MemoryWriteBack, InstallPack |
| **known gaps (10)** | AutonomousAgent, Crew, PlanExecute, InsightAction, MarketResearch, OwnerBriefing, Nurture, StaleChase, RentReminder, ShowingSchedule |

**Six of those ten reach a real customer or a real amount of money.**

`AutonomousAgentWorkflow` is named the largest, with the arithmetic and the reason it is
not closed here: a monitor is a second model call per run, which is a cost decision an
operator makes, not a fix to slip in. Its outcomes *are* recorded — the ledger, the reply
gate and the empty-result check all apply — but nothing judges the reply after the fact.

## The bug triage loop

See [ADR 21](../adr/021-the-repair-loop-never-edits.md). Runs the gate, classifies every
failure, and asks a model only about confirmed code defects. It never edits, commits,
pushes or migrates, and the test asserts the export surface cannot.

Against the live gate: *"2 environment problems and no code defect. Nothing is wrong with
the product."*
