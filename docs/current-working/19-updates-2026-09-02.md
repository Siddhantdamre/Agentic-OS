## The pattern behind almost all of it

Nine defects were found in two days. Eight share one shape: **a capability that
is built, correct, tested, and unreachable.** Nothing fails. No suite goes red,
because each suite creates its own fixtures and then asserts against them.

The question that finds this class is not "does it work" but **"has this ever
produced a row here?"**

The two that were not that shape were the opposite: a check that had gone red
and nothing was running it.

## 1. Inbound work reached one arbitrary employee

Employee selection on inbound was:

```sql
SELECT id, name, role, persona, tool_allowlist FROM ai_employees
 WHERE org_id = $1 AND status = 'active' LIMIT 1
```

No `ORDER BY`, no capability match. There was no routing at all.

Measured in the demo workspace before the fix:

| Employee | Actions | Threads owned |
|---|---|---|
| Priya (`provisioning`) | 6 | 8 |
| Sarah, Emma, Marcus, Aisha, Kabir, Meera, Research, Finance | 0 | 0 |

Eight employees marked `active`, holding distinct tool allowlists, throughput
zero. The permission model was genuinely enforced the whole time — it simply
never had work to govern.

Fixed by routing on the channel the message arrived on, which the allowlist
already encodes. See [ADR 16](../adr/016-route-by-capability-not-row-order.md).
Guard: `infra/scripts/check-inbound-routing.js`, 7/7, in `verify.js`.

## 2. Nothing in the system ran on a timer

No cron, no Temporal Schedule. The only `setInterval` calls are an SSE
keepalive and a widget embed. `insight-engine` — which dispatches
`StaleChaseWorkflow`, `NurtureWorkflow` and the owner briefing — fires only
when a human loads `/analytics`, `/insight` or Ask AI.

`OwnerBriefingWorkflow` had produced **zero rows in its entire history**.
`MarketResearchWorkflow` was referenced only in `workflows/index.ts` —
registered with the worker, started by nothing, anywhere.

The workflows never needed a scheduler; they end each run by sleeping to the
next slot and calling `continueAsNew`. They needed a first start.
See [ADR 17](../adr/017-recurring-work-schedules-itself.md).

**First briefings ever recorded**, 2 September 2026 12:45 UTC:

```
Sharma Properties, Thane │ Morning briefing: 1 unworked inquiries,
                         │ 3 open conversations, 1 threads need attention
Zoho                     │ Morning briefing: 0 unworked inquiries,
                         │ 1 open conversations, 0 threads need attention
```

The `3` agrees with what Ask AI and `/insight` reach independently. It was
produced **without model credit** — `narrateBriefingActivity` has a
deterministic fallback.

## 3. The briefing was written and never shown

`persistBriefingActivity` has always stored its result to `channel_logs` as an
`OWNER_BRIEFING` row carrying metric points, knowledge gaps and the narrative.
No screen had ever read one.

Added `GET /api/briefings` and `components/briefings/BriefingPanel.tsx`,
mounted on Home directly under the approvals queue. The panel shows the agent's
own words rather than re-deriving today's figures: a briefing records what the
agent understood when it looked, and recomputing would be a different and less
honest thing.

## 4. Research refused to work without a key it did not need

`researchTopicActivity` reached the web only through Jina *search*, so an org
with no `JINA_API_KEY` got an empty report reading "no search provider
configured" — even for competitor pages whose URLs the owner could supply.

Measured from inside the worker container with no key:

| Endpoint | Used by | Result |
|---|---|---|
| `r.jina.ai` | `web_extract`, research reading | **HTTP 200**, real page text |
| `s.jina.ai` | `web_search`, research discovery | **HTTP 401** |

Added an optional `urls` input read through the keyless reader. See
[ADR 18](../adr/018-searching-and-reading-are-separate.md). Verified with the
key deleted: the reason moved from "no search provider configured" to
"sources were retrieved but not analysed" — retrieval working, only synthesis
waiting on the model.

This also corrected `connectors-status.js`, which had counted the two as one
blocked provider. Real figure: **4 tools work today, 61 blocked** — not 3.

## 5. Employee activity had no surface

Every agent action has named its employee since the outcome ledger shipped, and
there was no way to see it. An operator could pause or delete an employee but
never answer the only question they ask: what has this thing been doing.

Added `GET /api/employees/[id]` and `/employees/[id]`, with the roster card
name linking to it — a detail page nothing links to is a page that does not
exist. Every field is a persisted row; where there are no rows the page says
so rather than printing a plausible zero.

## 6. Smaller corrections

- **OAuth popup dialled an unresolvable host.** `/api/integrations/nango-token`
  handed the browser `http://nango-server:3003`, a compose service name. OAuth
  would have failed silently with a blank popup the moment a real client id
  existed. Guard: `check-nango-browser-host.js`, 11/11.
- **The honest refusal rendered off-screen.** The connectors error banner was
  in-flow at the top of a 4,700px scroll container while the button that
  triggers it sits ~3,000px down. Made sticky and opaque.
- **The Ask AI greeting promised a tool the agent refuses.** It hardcoded
  "always available: … web_search …". Now computed from the environment.
- **`Conversations 9, -100% vs yesterday`.** The headline was an all-time
  `COUNT(*)`; the delta compared two 24-hour windows. Two different quantities
  in one card. Replaced with an absolute count over a stated window.
- **The tenant-scope lint could be fooled by a comment.** It scanned raw source
  for backtick spans, so a comment backtick re-paired every backtick after it,
  and — worse — the word `org_id` in a nearby *comment* could certify a
  genuinely unscoped query. Comments are now blanked in place before scanning,
  preserving offsets. That closed a **false pass** on the tenant-isolation gate.
- **A demo script was red and nothing ran it.** `demo-ai-employee.js` asserted
  `COUNT(employee_id) = COUNT(*)` and broke the first time anyone used the Ask
  AI console. It was not registered in `verify.js`, so the gate reported SOUND.
  Now registered. See "Attribution" below.

## Operational traps found the hard way

Recorded because each cost real time and none is discoverable from the code.

**The worker polls `darex-agent-tasks`.** Hardcoded in `services/workflows/src/worker.ts`,
and `TEMPORAL_TASK_QUEUE` is empty in the worker container. A workflow started
on any other queue sits at `historyLength: 2` — `RUNNING`, never picked up,
with no error anywhere.

**Never `localhost` from the host; always `127.0.0.1`.** Node resolves
`localhost` to IPv6 `::1` first. Docker publishes on `[::]` too, but that path
resets the connection, so a Temporal client times out after 5s against a
cluster that is healthy and listening, and `pg` reports "Connection terminated
unexpectedly". `check-e2e-inbound.js` documents the same trap for HTTP.

**Docker Desktop lives under `%LOCALAPPDATA%\Programs\DockerDesktop`,** not
Program Files.

**The Next.js production build needs more RAM than this machine reliably has.**
Builds die with `failed to receive status: rpc error: … EOF`. The machine has
15.7 GB with ~0.5 GB free; `ServiceShell` (Dell SupportAssist) alone holds
2.76 GB. Stopping the Langfuse stack frees 2.47 GB — it is 61% of idle memory
and sits behind the `observability` compose profile:

```bash
docker stop darex-langfuse-server darex-langfuse-worker \
  darex-langfuse-clickhouse darex-langfuse-minio darex-langfuse-redis
```

Build with as little else running as possible.

**After a Docker Desktop restart the port proxy is unreliable.** TCP connect
succeeds while no data flows, so `pg` and Temporal clients fail from the host
against healthy containers. `docker compose restart postgres` re-establishes
it. Running the work from inside a container (`docker exec darex-worker node -e …`)
avoids the proxy entirely and is the more reliable path for one-off tasks.

## Running the recurring work

```bash
# report only — which workspaces qualify, and how many briefings they have had
node infra/scripts/start-recurring-work.js

# actually start the daily briefing loops
node infra/scripts/start-recurring-work.js --start --hour 8 --tz Asia/Kolkata
```

Idempotent: the workflow id is `owner-briefing:<orgId>`, so a second run
reports "running" rather than creating a second loop.

Only workspaces with more than one active employee **and** at least one
conversation are started. This deliberately excludes test residue — there are
**52 orgs named "Bright Leaf Interiors"**, one employee each, left behind by a
suite that provisions a workspace per run.

To stop one:

```bash
docker exec -i darex-worker node -e '
const { Connection, Client } = require("@temporalio/client");
(async () => {
  const connection = await Connection.connect({ address: "temporal:7233" });
  const client = new Client({ connection, namespace: "default" });
  await client.workflow.getHandle("owner-briefing:<ORG_ID>").terminate("stopped by operator");
  await connection.close();
})();'
```
