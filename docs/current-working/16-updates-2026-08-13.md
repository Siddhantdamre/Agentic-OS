## Ask AI

**What was broken.** The page streamed NDJSON but the terminal `done` event
was overwritten by later local state, so the final answer could vanish. The
pooled DB client was held across classify/plan/agent calls (pool `max: 10`).
LiteLLM used to ship a hardcoded key/URL path. Chat history lived only in
`localStorage`. Home’s `/ask-ai?q=` bootstrap was unreliable. Added plan
instructions were a fake `agent.user_instruction` tool. Execute could re-run
a completed plan. `VALID_TOOLS` omitted several Google products the catalog
already listed.

**What changed.**

- `ask-ai/page.tsx` applies `event.type === 'done'` (and `'simple'`) to the
  in-flight AI message: final `answer`, `usedTools`, `error`, `retryable`.
- `POST /api/ask-ai` loads org/user/channels, persists the user row into
  `messages`, then **releases the client before** `classifyRequest` /
  `generatePlan` / `runAutonomousAgentDirect`.
- `lib/litellm-client.ts` requires `LITELLM_API_KEY` or `LITELLM_MASTER_KEY`.
  Production also requires `LITELLM_BASE_URL`. There is no shipped API key.
  Non-production still defaults the URL to `http://localhost:4000/v1` if unset.
- Atomic-agent session key is `askai-{userId}-{YYYYMMDD}`.
- Canonical thread is a `conversations` row with `metadata.source = 'ask-ai'`
  plus `messages`. `GET /api/ask-ai` hydrates that thread and recent
  `agent_plans`. `localStorage` is a cache only.
- Home still redirects to `/ask-ai?q=…`; the page reads `q` once and sends it.
- Welcome copy and suggestion chips are honest: they do not claim connectors
  the org does not have (`requires:` filters chips). `notConnected` tool events
  surface Connect + `setupUrl` (default `/connectors`).
- Plans reload from `GET /api/ask-ai` so a refresh does not drop a pending
  PlanCard. `PATCH /api/ask-ai/plan` persists toggles and extra instruction
  steps. Execute treats `user_instruction` / `note` / `agent.user_instruction`
  as **skipped notes**, not as MCP tools.
- `GET /api/ask-ai/execute` returns **409** if the plan is already
  `completed`, `completed_with_errors`, or `cancelled`. After the user
  approves, the step loop **keeps running if the SSE client disconnects**;
  only event enqueue is skipped.
- `VALID_TOOLS` now includes `google-analytics`, `google-chat`, `google-meet`,
  `google-search-console`, `google-business-profile`, `google-cloud`.

**What now works.** Simple stream with a visible final answer; complex
plan → approve → parallel execute; history across refresh; Home deep-link;
honest empty-state suggestions.

**Still on this path.** Classifier can mis-tag (bias to simple). No
multi-user shared Ask AI thread. Gmail draft/send still needs a token with
`gmail.compose`.

## Agent runtime and tools

**What was broken.** `AutonomousAgentWorkflow` wrote `priorToolResults` and
never read them; `isDone` was unset, so the extra loop was inert.
`idempotency_keys` existed and activities ignored it. `/api/agent/stream`
died if Temporal was down. `/api/agent/tools` GET was unauthenticated.
Several MCP names were registered with stub/`Unhandled Google tool`
executors. Razorpay only looked at process env. Worker process exited on
Temporal connect failure.

**What changed.**

- Workflow: at most **3** durable turns. `mapTurnToResult` sets `isDone`
  when there is a reply or no tools. The next turn receives
  `priorToolResults` (last 12 steps) so the model is not asked to blindly
  re-run work. `runAgentTurnActivity`, `saveMessageActivity`, and
  `logChannelActivity` read/write `idempotency_keys`.
- Worker: exponential reconnect backoff 2s → 30s instead of a fatal exit.
- MCP bridge: server name still `darex`. **62** `mcp.darex.*` tools (was 49).
  `GET /health` (and `/`) return liveness. Newly registered: `code_execution`,
  `stripe_create_customer`, `stripe_get_customer`, `intercom_reply`,
  `intercom_create_conversation`, `chat_list_spaces`, `chat_send_message`,
  `meet_create_space`, `meet_get_space`, `search_console_sites`,
  `search_console_query`, `business_list_locations`, `cloud_list_projects`.
  `analytics_report` is no longer a stub in the executor.
- Google Chat / Meet / Analytics / Search Console / Business Profile / Cloud,
  Intercom write, and Stripe customer ops call the real APIs when a Nango
  token exists, otherwise `notConnected()`. They are **not** simulated.
- Razorpay: `channels.meta` (`keyId`/`key_id` + secret) first, then
  `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET`, then `notConnected`.
- `POST /api/agent/run` and `POST /api/agent/stream`: Temporal first, direct
  `runAutonomousAgentDirect` fallback. DB client released before the agent.
  Assistant message is saved only on the **direct** path (workflow already
  saves). Stream handle is typed
  `Awaited<ReturnType<typeof startAutonomousAgentWorkflow>> | null`.
- `GET /api/agent/tools` requires a session (`getScopedClient`).
- Allowlist matching stays case-insensitive and treats `_` / `-` as equal.
- `web_search` / `web_extract` require `JINA_API_KEY` (or `JINA_READ_API_KEY`);
  no fake results.

**What now works.** Durable Temporal wrapper that actually uses its retry
fields; agent/stream survives Temporal downtime; MCP surface matches the
executor for the extra Google/Intercom/Stripe tools **when connected**.

**Catalog lag.** `lib/integrations-catalog.ts` still marks several of those
Google products `catalog_only` with operator hints that say “no executor
yet.” The **executor and MCP list are the source of truth**; the catalog
hints are stale. Google Cloud remains `service_account` in the UI (no OAuth
popup) even though `cloud_list_projects` exists on MCP.

## Auth and tenancy

**What was broken.** Invite and reset-password pages were missing or
unreachable once signed in. OAuth dropped `?invite=`. Body `org_id` was
still accepted in some org routes. RLS `set_config` needed a shared helper
for webhook/background callers.

**What changed.**

- `getScopedClient()` and `getOrgScopedClient(orgId)` both
  `set_config(..., false)` (session-level) and `RESET` org/user GUC on
  `release()`. Webhooks use `getOrgScopedClient` after resolving tenant via
  SECURITY DEFINER functions — they do not trust JSON `org_id`.
- New pages: `/forgot-password`, `/reset-password`, `/invite/[token]`.
  Middleware `isAuthenticatedPublicPath` lets a signed-in user hit invite
  accept and reset-password instead of bouncing to `/`.
- OAuth start reads `invite` and keeps it through the callback state.
- `POST /api/org/create` and `POST /api/org/onboarding` **400** if the body
  contains `org_id` / `orgId`. Same pattern on Settings.
- Migration `009_auth_tenancy.sql`: unique `lower(email)`, `org_invites`,
  `password_reset_tokens`, `users_self_select`, auth SECURITY DEFINER
  helpers so `darex_app` can look up a user before org scope is set.

**What now works.** Session RLS for both cookie and webhook callers; invite
token accept; password reset tokens; OAuth invite round-trip.

**Still.** App default `DB_USER` is still `darex` (superuser). Switching to
`darex_app` is optional; migration 011 grants CONNECT/table rights. Demo
OAuth (`ALLOW_DEMO_AUTH`) remains dangerous in prod. Middleware still does
not force onboarding solely from DB state — it uses the `darex_onboarding`
cookie.

## Integrations and Nango

**What was broken.** UI could show Connected without a Nango row. Disconnect
left the Nango connection. WhatsApp BYOK stored tokens without a Graph ping.
Razorpay was env-only. Shopify/Zendesk OAuth popped without shop/subdomain.
Test proxy could perform writes. Missing OAuth client IDs failed opaquely.

**What changed.**

- `GET /api/integrations` re-checks Nango (`{orgId}_{provider}`) before
  calling a row connected. `POST connect` 400s with `nangoUiUrl` if the
  connection is missing.
- `POST disconnect` calls `deleteNangoConnection` then clears `channels`.
- WhatsApp BYOK (`POST /api/integrations/whatsapp`) Graph-pings via
  `pingWhatsApp` before writing `channels.meta`.
- Razorpay (`POST /api/integrations/razorpay`) verifies keys with
  `pingRazorpay`, stores them in `channels.meta`.
- Connectors UI requires Shopify `shopDomain` and Zendesk `subdomain`
  before `nango.auth`. Those values are passed as Nango `subdomain`.
- `POST /api/integrations/test` is a **read-only ping** by default
  (`pingNangoProvider` / `pingWhatsApp` / `pingRazorpay`).
- Browser helper surfaces “paste a real OAuth client ID in the Nango UI
  (`http://localhost:3003`)” when Nango says the client is unconfigured.

**What now works.** Connected means Nango agrees. WhatsApp/Razorpay BYOK
fail closed on a bad token. Shopify/Zendesk cannot start OAuth without the
extra id.

**Still operator.** Real OAuth client IDs for HubSpot, Stripe, Notion,
Slack, Shopify, Zendesk, Intercom, Meta Ads, and most Google products that
are not already configured. `NANGO_SECRET_KEY` must be Nango’s UUID.

## Webhooks and inbox

**What was broken.** WhatsApp POST did not verify `X-Hub-Signature-256`.
Chatwoot ingested + SSE’d and **did not start the agent**. Inbox
`POST /api/inbox/send` returned `{success:true}` without sending. Org could
be taken from the body. Conversation `chatwoot_conv_id` was globally unique
(cross-tenant collision).

**What changed.**

- WhatsApp: `assertMetaWebhookSignature` on the raw body. Org via
  `resolve_whatsapp_channel` / WABA / single-org helpers (migration 010),
  never from the JSON body. Persist → **200 immediately** →
  `fireInboundAgent` (Temporal, then direct). Reply saved (if the workflow
  did not) and sent on Graph.
- Chatwoot: HMAC when `CHATWOOT_WEBHOOK_SECRET` is set. `void payload.org_id`.
  Org from `?org_id=`, `Authorization` matching `orgs.meta.webhook_secret`,
  `X-Darex-Org-Id`, or single-active-org. After persist it **does** call
  `fireInboundAgent`.
- Shared `lib/inbound-agent.ts` for WhatsApp, Chatwoot, and dashboard
  conversation inbound.
- Inbox gateway signs with HMAC and forwards outbound to
  `POST /api/webhooks/outbound`, which resolves org from the conversation
  row and `sendChannelReply`. Compose passes `CHATWOOT_WEBHOOK_SECRET` into
  the inbox container.
- Conversations UI: org-scoped SSE; human-agent replies call
  `sendChannelReply` on the channel.
- Migration `010_webhook_inbox.sql`: `orgs.meta`, per-org unique Chatwoot
  conversation ids, inbound message idempotency on `(org_id, chatwoot_msg_id)`,
  SECURITY DEFINER resolvers.

**What now works.** Signed inbound; Chatwoot actually talks to the agent;
human send-back on the channel; inbox gateway is no longer a fake-success
stub.

**Still.** WhatsApp **outbound Graph** 401 until `META_ACCESS_TOKEN` (or the
per-channel token in `channels.meta`) is rotated. Last recorded live E2E
was inbound+LLM 5/5 with outbound 401 (token expired 2026-06-12). Realtime
hub is still in-process (one Next.js process).

## Dashboard and infra

**What was broken.** Some KPI pages had leftover hardcoded numbers.
Settings Meta webhook URL pointed at `/api/webhooks/chatwoot`. Invites
inserted a placeholder user and sent no email. `infra/docker/sandbox/` was
absent so compose could not build code-exec. Custom SKILL.md playbooks were
not copied into the atomic-agent image. Langfuse shared Redis with Nango
(~100 clients) and ClickHouse persistence was flaky. Compose `env_file`
failed if a listed file was missing. No dashboard liveness route.

**What changed.**

- Home `/api/dashboard/stats`, analytics, insight, employees all go through
  `getScopedClient` and SQL. Insight is still **rule templates**, not an
  LLM insight engine — but the counts are real. Home has no fake `99.8%`.
- Settings GET returns distinct `metaWebhookUrl` (`/api/webhooks/whatsapp`)
  and `chatwootWebhookUrl` (`/api/webhooks/chatwoot?org_id=`). Invites write
  `org_invites` and try Resend; if `RESEND_API_KEY` is unset the API still
  returns a **copyable `inviteUrl`**.
- Migration `011_employees_app_role.sql`: `ai_employees.graph_id` default
  `''`; `GRANT CONNECT` + table/sequence rights to `darex_app`.
- `infra/docker/sandbox/` restored in the working tree (`Dockerfile` +
  `server.mjs`, unprivileged uid 10001, python/node/bash). Compose service
  `sandbox` can build. **Not in commit `99b5f04`** — still untracked.
- atomic-agent Dockerfile `COPY custom-skills ./custom-skills` and merges
  them into `starter-skills`.
- Dedicated `langfuse-redis` service; Langfuse server/worker point at it.
  Shared `redis` remains for Nango.
- Compose `env_file` entries use `required: false`. Root `.env.example`
  lists names only.
- `GET /api/health` → `{ ok: true, service: 'dashboard' }` (no session).
- Compose now has **19** services (added `langfuse-redis`; sandbox context
  present in the tree).

**What now works.** Honest KPIs; correct webhook URLs; invite links;
sandbox image buildable from this tree; custom skills in the agent image;
Langfuse no longer fights Nango for one Redis.
